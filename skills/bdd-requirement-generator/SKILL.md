# BDD 需求文档生成器

## 描述

将产品需求原始描述（散文、列表、wiki 链接等）转换为标准 BDD（Behavior-Driven Development）格式的需求文档。输出文件放在 `docs/` 目录下，文件名使用 kebab-case 并以 `-bdd.md` 结尾。

## 触发条件

当用户提到以下关键词时激活此技能：

- "BDD"、"BDD格式"、"BDD需求"
- "行为驱动"
- "Given/When/Then"

## 输入

用户提供以下任意一种或组合：

1. 需求原始文本描述（散文、列表）
2. Confluence wiki 链接（使用 `mcp_guazi_wiki_get_wiki_page` 工具读取）
3. 已有的需求文档文件路径

## 输出

一份完整的 BDD 格式 Markdown 文档，**章节顺序固定**如下：

```markdown
# {模块名称} — BDD 需求文档

## Feature: {功能描述}

作为 {角色}，
我希望 {期望行为}，
以便 {业务价值}。

{可选：Tab 显隐总则、模块位置说明等产品级补充，仍使用产品语义，不写代码字段}

---

### Scenario N: {场景名称}

**Given** {前置条件 — 产品语义}
**When** {触发动作}
**Then** {预期结果}
**And** {附加结果}（可选）

---

## 接口文档

{接口路径、入参/出参、字段含义；联调前可标「待确认」}

---

## 数据依赖说明

| 数据项 | 来源 | 说明 |
| ------ | ---- | ---- |
| ...    | ...  | ...  |

---

## 埋点方案汇总（如有埋点需求）

| 埋点名称 | pagetype | pagekey | tracking_type | module(区域) | action(模块) | position(位置) | extra |
| -------- | -------- | ------- | ------------- | ------------ | ------------ | -------------- | ----- |
| ...      | ...      | ...     | ...           | ...          | ...          | ...            | ...   |

---

## 前后端职责划分

### 后端负责（前端只消费结果，无需实现逻辑）

| Scenario   | 说明       | 原因                                           |
| ---------- | ---------- | ---------------------------------------------- |
| Scenario X | {场景名称} | {为何由后端处理，如：聚合计算、数据抓取逻辑等} |

### 前端负责

| Scenario   | 说明       | 核心实现点                                                         |
| ---------- | ---------- | ------------------------------------------------------------------ |
| Scenario X | {场景名称} | {前端需要实现的具体逻辑，如：渲染条件判断、登录态处理、埋点上报等} |
```

## 工作流程

### 步骤 1：收集需求信息

- 如果用户提供了 wiki 链接，使用 `mcp_guazi_wiki_get_wiki_page` 读取内容
- 如果用户提供了文本描述，直接解析
- 如果信息不完整，向用户确认关键细节

### 步骤 2：识别场景

从需求中提取所有行为场景，按以下分类覆盖：

1. **正常展示场景** — 模块/组件在正常数据下的展示行为
2. **条件分支场景** — 不同数据条件下的差异化展示（如有/无补贴）
3. **交互场景** — 用户操作触发的行为（点击、滑动等）
4. **权限/状态场景** — 登录/未登录、权限校验等
5. **异常/兜底场景** — 接口异常、数据为空时的降级处理
6. **埋点场景** — 曝光和点击埋点上报（如有埋点方案）

### 步骤 3：编写 Feature 与 Scenario（产品语义）

遵循以下规则：

- 每个 Scenario 只描述一个独立的行为
- **Given / When / Then / And 一律使用产品语义**，描述用户可理解的业务状态与结果
- **禁止**在 Feature 章节（含 Scenario）中写入实现层字段或 Store 路径，例如：
  - ❌ `carSlice.carSourceStatus === 0`
  - ❌ `experimentSlice.financialChainOpt`
  - ❌ `carOtherInfo.showInstallmentTab`
- **推荐**写法示例：
  - ✅ `车源为新车`
  - ✅ `已命中金融链路实验`
  - ✅ `支持分期购车`
  - ✅ `同款在售模块已展示 Tab 区域`
- When 描述触发动作（用户操作或系统事件）
- Then 描述可验证的预期结果（界面表现、文案、模块显隐等）
- 使用 And 连接同一层级的多个条件或结果
- 场景编号连续，标题简洁明确
- 埋点场景中，埋点参数可在 **埋点方案汇总** 或 **接口文档** 中以 `code` 等形式标注；Feature 内仍用产品语义描述「曝光」「点击」行为

### 步骤 4：编写接口文档

紧接在 Feature 全部 Scenario 之后，单独增加 **`## 接口文档`** 章节：

- 列出本需求依赖的接口（路径、方法、所属服务，能确定则写清，否则标「待确认」）
- 说明与 Scenario 相关的**请求参数、响应字段、枚举取值**（可引用后端 wiki / YAPI）
- 建立 **产品语义 → 接口字段** 对照（便于研发联调，与 Feature 用语一致）
- 接口尚未对齐时，保留章节骨架并标注「待联调确认」，**不得**因此回退到在 Scenario 里写 `slice.*` 字段

接口文档章节示例结构（可按需裁剪）：

```markdown
## 接口文档

### {接口名称或用途}

- **路径**：`待确认` 或 `/api/...`
- **说明**：...

| 产品语义（Feature 用语） | 响应字段（待确认）   | 类型    | 说明 |
| ------------------------ | -------------------- | ------- | ---- |
| 支持分期购车             | `showInstallmentTab` | boolean | ...  |
```

### 步骤 5：补充数据依赖说明

在 **接口文档之后** 编写 **`## 数据依赖说明`**：

- 汇总模块依赖的数据项、来源（主接口 / 独立接口 / Store / 实验服务等）
- 可与接口文档字段交叉引用，侧重「前端消费视角」的依赖清单
- 字段名、路径写在本节或接口文档，**不**写回 Feature Scenario

### 步骤 6：埋点与前后端职责

- **埋点方案汇总**：若需求含埋点，以表格汇总 pagetype、moduleId 等参数
- **前后端职责划分**：遍历 Scenario 归类（见下方判断标准）

**归入「后端负责」的 Scenario 特征：**

- 涉及多接口数据聚合计算（如：价格 = A - B - C）
- 涉及数据优先级抓取逻辑（如：优先取工单，无则取资产）
- 涉及状态机检测与重试（如：检测到停售后重新抓取）
- 前端只需消费最终字段（如 `show`、`replacePrice`），不感知计算过程

**归入「前端负责」的 Scenario 特征：**

- 根据接口字段决定渲染/隐藏（如 `show=true/false`）
- 根据登录态切换展示内容（如：未登录展示兜底文案）
- 用户交互行为（点击、跳转、唤起登录等）
- 登录回调后的二次数据拉取与状态更新
- 接口异常时的降级展示
- 埋点曝光/点击上报

输出两张表格：后端负责表、前端负责表。

### 步骤 7：输出文件

- 文件路径：`docs/{feature-name}-bdd.md`
- feature-name 使用 kebab-case 命名

## 场景覆盖检查清单

生成文档后，自检是否覆盖了以下维度：

- [ ] 文档章节顺序：Feature → 接口文档 → 数据依赖说明 →（埋点）→ 前后端职责划分
- [ ] Feature 内 Scenario 的 Given/When/Then 均为产品语义，无 `slice.*`、Store 路径、未对齐的接口字段
- [ ] 接口文档已单独成节，含产品语义与字段对照（或明确待确认）
- [ ] 数据依赖说明位于接口文档之后
- [ ] 模块在页面中的位置（可在 Feature 总则或 Scenario 中体现）
- [ ] 正常数据下的完整展示
- [ ] 条件分支（有/无某数据时的差异）
- [ ] 用户交互行为及结果
- [ ] 登录/未登录状态处理（如适用）
- [ ] 接口异常或无数据时的降级
- [ ] 埋点曝光与点击上报（如有）
- [ ] 前后端职责划分已生成，每个 Scenario 均已归类

# Mode B：业务场景分析（已有代码 → 场景梳理）

> **与 Mode A 的区别**：Mode A 是"需求 → BDD"的正向生成；Mode B 是"已有代码 → 场景梳理"的逆向分析。当用户说"梳理""分析展示情况""什么情况展示哪部分"时使用 Mode B。

## 触发条件

当用户提到以下关键词时激活 Mode B：

- "梳理"、"分析展示情况"、"场景分析"
- "什么情况展示哪部分"、"各场景的代码"
- "组件逻辑梳理"、"条件分支分析"

## 输入

用户提供以下任意一种或组合：

1. 组件文件路径（如 `src/pages/index/features/NewEnergy/NeFinanceStage/index.tsx`）
2. 组件目录路径（自动扫描 `index.tsx` 及子组件）
3. 业务场景描述（如"金融组件有5种展示场景"）

## 输出

一份结构化的场景分析文档，输出到**组件同级目录**，文件名使用 `SCENARIO.md`：

```
src/pages/index/features/NewEnergy/NeFinanceStage/SCENARIO.md
```

## 文档结构（固定）

```markdown
# {组件名称} — 业务场景分析

## 概述

{一句话说明组件职责和它在页面中的位置}

---

## 场景清单

### Scenario 1: {场景名称}

**条件**：{触发该场景的数据条件，使用产品语义}

**展示内容**：

- {展示的 UI 元素 1} → 对应代码 `{文件路径}:{行号范围}`
- {展示的 UI 元素 2} → 对应代码 `{文件路径}:{行号范围}`

**不展示**：

- {在该场景下隐藏的元素}

---

### Scenario 2: {场景名称}

...（同上格式）

---

## 条件矩阵

| 场景  | 条件1 | 条件2 | 条件3 | 展示模块 |
| ----- | ----- | ----- | ----- | -------- |
| 场景1 | ✅    | ❌    | ✅    | A, B     |
| 场景2 | ❌    | ✅    | ✅    | A, C     |
| ...   | ...   | ...   | ...   | ...      |

---

## 代码入口索引

| 场景  | 入口文件    | 关键行号 | 核心判断逻辑                          |
| ----- | ----------- | -------- | ------------------------------------- |
| 场景1 | `index.tsx` | L85-99   | `experimentSlice.xxx && carSlice.yyy` |
| ...   | ...         | ...      | ...                                   |

---

## 待确认项

- {分析过程中无法确定的条件或行为}
- {需要与产品/后端确认的逻辑}
```

## 工作流程

### 步骤 1：读取组件代码

- 读取用户指定的组件文件（`index.tsx` 及相关子组件）
- 识别组件中的条件分支（`if`/三目运算符/逻辑与/`&&`）
- 识别涉及的 Store 字段（`usePageStore`、`useXxxStore`）

### 步骤 2：提取所有条件

从代码中提取所有影响展示的条件，包括：

1. **实验组条件** — `experimentSlice.xxx` 相关判断
2. **数据条件** — 接口返回字段（如 `carSourceStatus`、`showInstallmentTab`）
3. **业务类型条件** — 新能源/燃油车/自营门店等
4. **组合条件** — 多个条件的 AND/OR 组合

### 步骤 3：穷举场景组合

基于提取的条件，穷举所有可能的展示组合：

- 每个组合对应一个 Scenario
- 标注每个 Scenario 下哪些 UI 元素展示、哪些隐藏
- 记录每个 Scenario 的代码入口行号

### 步骤 4：生成条件矩阵

用表格形式展示所有场景的条件组合，便于快速查阅。

### 步骤 5：输出文档

- 文件路径：`{组件目录}/SCENARIO.md`
- 使用 PascalCase 目录名（组件目录名）+ `SCENARIO.md`

## 场景分析检查清单

生成文档后，自检：

- [ ] 所有条件分支均已覆盖（无遗漏的 `if`/三目/`&&`）
- [ ] 每个 Scenario 标注了代码入口行号
- [ ] 条件矩阵穷举了所有组合
- [ ] 条件使用产品语义描述（不直接写 Store 字段路径在 Scenario 标题中）
- [ ] 代码入口索引中可包含 Store 字段（方便定位）
- [ ] 待确认项已列出无法确定的逻辑
