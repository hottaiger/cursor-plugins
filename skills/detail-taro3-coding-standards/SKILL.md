# detail-taro3 编码规范

**模式**：工具封装 + 审查器（细则在 `references/`，按需加载，避免重复占用上下文）。

## 何时激活

- 用户要求按**本项目**规范编写、重构或解释代码
- 用户询问「该怎么写」「是否符合规范」「帮忙 review」
- 审查 PR、diff 或指定文件是否符合仓库约定

## 编写代码流程

1. 读取 [references/conventions.md](references/conventions.md)，将其中与当前任务相关的条目作为准则。
2. 若涉及 Koala UI 或 Less 结构，再加载上表对应 Skill。
3. 修改代码时：匹配现有文件的命名、导入方式与目录习惯；不扩大改动范围。
4. 提交说明需符合 [references/conventions.md](references/conventions.md) 中的 Git 与 commitlint 约定。

## 抽象逻辑注释规范（重要）

当新增或重构抽象逻辑（如自定义 hook、工具函数、适配层、公共 service）时，必须补充“可使用”的说明注释，避免仅凭命名猜测用途。

- 必须说明 **使用场景**：该抽象解决什么问题、适用于哪些业务条件。
- 必须说明 **使用方法**：如何在调用方接入（最小示例或关键调用方式）。
- 建议说明 **返回值/参数语义**：尤其是布尔值、状态码、枚举值的业务含义。
- 注释应聚焦“为什么/何时用”，避免无信息量描述（如“给变量赋值”）。
- 若抽象行为依赖平台差异（RN/H5/小程序），需在注释中明确平台约束。

## 代码审查流程

1. 读取 [references/review-checklist.md](references/review-checklist.md)。
2. 先理解变更意图与影响范围，再逐项对照清单。
3. 对每个问题标注：**位置**（文件与大致行号或片段）、**严重程度**（见下）、**原因**、**修复建议**（可附修正示例）。
4. 输出结构化报告，建议包含：
   - **审查摘要**：变更目的、整体评价
   - **问题发现**：按严重程度分组 — **错误**（必须修复）→ **警告**（建议修复）→ **提示**（可选优化）
   - **评分**：1–10 分及简要理由（若用户需要）
   - **核心建议**：少量高价值项

### 严重程度

- **错误**：违反 commitlint/明显破坏 Lint 规则、类型安全约定、或会造成运行时/构建失败的问题。
- **警告**：可维护性、一致性、hooks 依赖等与项目习惯明显不符。
- **提示**：命名、注释、微优化等。
